⏺ I've added a "Stage 3 — decisions to pick" section to the end of design.md.
  It's all multiple choice with my pick marked ✔. I wrote no code and made no
  commits.

  Feature (F). I compared Arrays, Coroutines, Inheritance and Overloading across
  lexer, parser, checker and codegen, plus the IR excerpt and how visible each
  is in a program. My pick is Arrays. Every required item can be shown by a
  test. It builds on rules Kaguya already has: constant by default, 🔓 on every
  step of a chain, and objects that are never copied. The run-time bounds error
  also makes a good demo.

  Loops are too thin. Stage 2 already has 🔁, the back edge, a loop inside a
  loop, and a body that declares a variable. That leaves only for and break, and
  the handout wants a feature "not built in class".

  Arrays (A1–A9). My picks, one rule each:
  - Elements are built-in types only.
  - The size goes after the type: 3⃣[9] 🔓 b ⟨0⟩.
  - A single initial value fills the whole array.
  - Arrays are allowed as struct fields.
  - Indexing is one-dimensional.
  - A constant index out of range is a compile error. Any other index is checked
    at run time and fails with a message on stderr and exit code 1.
  - Function parameters are sized, and only array parameters may be marked 🔓.
  - 📢 prints an array as [1, 0, 2].

  Optimizer (O1–O9). My picks:
  - Reading a variable: a read is matched by the declaration it points to, not
    by name, so shadowing is handled for free.
  - Self-updates: a variable's use inside its own update (x := x + 1) doesn't
    count as a read.
  - Calls and 📥: any variable whose value calls a function or 📥 is kept whole.
  - Unused functions: found by reachability from main.
  - Inlining: only straight-line bodies. These are left alone:
    - an exit inside an 🤔 or 🔁
    - member functions
    - functions with array parameters
    - recursive functions
    - calls in a 🔁 condition
    - calls sharing a statement with another call or 📥
  - Renaming: inlined names become add.a, add.s, with add.0 for the result. An
    identifier can't contain ., so these can never clash with the caller's
    names.
  - No re-check: the checker doesn't run again after optimizing. A re-check by
    name would get a global wrong where the caller shadows it.

  Real program (P). Kaguya only has ==, ≠ and + - *, so every idea had to avoid
  <, / and %. My pick is tic-tac-toe:
  - a Board struct with a cells array
  - a member 🔓 place that refuses a taken cell
  - a function wins that checks the eight lines
  - moves read with 📥

  The other three ideas are a vending machine, a polynomial evaluator and a
  memory-pairs game.

⏺ Title

  Stage 3: arrays, optimizer, tic-tac-toe

  Description

  ## Feature: arrays

  Fixed-size arrays of `i32`, `i64` or `bool`:
  - the size is part of the type: `3⃣[9] 🔓 cells ⟨0⟩`
  - index read and write, with an `i32` or `i64` index
  - a literal index out of range is a compile error
  - any other index is checked at run time: a one-line error on stderr, then
  `exit(1)`
  - arrays can be struct fields
  - arrays are passed to functions by reference; a `🔓` parameter lets the
  function write the caller's array
  - `📢` prints `[1, 0, 2]`

  `<` and `>` are added as plain comparisons, so the program can reject a bad
  move. They support the program and are not the feature.

  ## Optimizer (`--optimize`)

  - **Unused functions:** found by reachability from the top level. A member
  function called anywhere counts as used.
  - **Unused variables:** matched by declaration, so shadowing is safe. Calls
  and `📥` are never dropped, and arrays are never removed.
  - **Inlining:** a function called exactly once is replaced by its body, with
  names renamed to `f.x` and the result in `f.0`. The README lists which shapes
  are left alone.

  The passes repeat until nothing changes. The whole suite also runs with the
  flag.
